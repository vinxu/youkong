## 二、"先计划、再确认、再执行"框架评估

### 框架遵守情况

| 阶段 | 预期行为 | 实际表现 | 评分 |
|------|---------|---------|------|
| 计划 | 用户输入 → 生成时刻表草案 | ✅ 正确生成 schedule 事件 | 90% |
| 确认 | 用户确认 → 触发 confirmed | ✅ Tool Calling 完美工作 | 100% |

### 框架问题

1. **无明确的"等待确认"状态提示** - 用户不知道需要确认
2. **取消后无清理确认** - 取消后直接结束，无反馈

## 三、发现的问题及严重程度

### 🔴 高优先级问题

#### 1. 时间格式畸形
```
问题: LLM 返回 "12:5"、"19:60"、"17:8" 等无效时间
影响: 前端显示异常，可能导致崩溃
示例: "end_time":"12:5" 应为 "12:05" 或 "17:00"
```

#### 2. 多轮对话时刻表不累积
```
问题: 每轮只返回当前时段，之前时段丢失
影响: 用户无法看到完整的一天安排
示例: 用户说了5个时段，最后只保存1个
```

#### 3. 修改时间逻辑错误
```
问题: "改到11点" 返回 "15:00"
影响: 用户意图被错误理解
原因: LLM 对"改"的理解可能混淆了原时间和新时间
```

### 🟡 中优先级问题

#### 4. 查询功能返回类型错误
```
问题: "查看今天安排" 返回 chat 而非 schedule
影响: 前端无法正确展示时刻表
```

#### 5. 部分响应为空
```
问题: 某些对话轮次返回空响应
影响: 对话中断，用户体验差
```

### 🟢 低优先级问题

#### 6. 模糊时间推理不准确
```
问题: "待会儿" 解析为固定时间可能不合理
影响: 用户需要手动纠正
```

#### 7. 日期识别偶尔出错
```
问题: "周六"、"后天" 等相对日期计算
影响: 偶尔安排到错误日期
```

## 五、迭代改进建议

### 立即修复（P0）

1. **时间格式强校验和修正**
   ```go
   // 在 sanitizeLLMTimeString 中增强处理
   - 处理单位数分钟: "12:5" -> "12:05"
   - 处理无效分钟: "19:60" -> "20:00"
   - 处理单位数小时: "9:00" -> "09:00"
   ```

2. **修复多轮对话时刻表累积**
   ```go
   // handleLLMResult 中合并时刻表
   newSchedule = mergeSchedules(session.CurrentSchedule, result.Schedule)
   ```

### 短期优化（P1）

3. **改进修改逻辑 Prompt**
   - 明确指示 LLM：修改时只改变指定的属性
   - 添加修改前后对比的推理要求

4. **修复查询功能**
   - 查询类输入返回 `is_query: true` 的 schedule 事件

5. **增加"等待确认"状态反馈**
   - 生成时刻表后明确提示用户确认

### 中期优化（P2）

6. **增强上下文保持**
   - 在 session 中保存完整对话历史摘要
   - LLM 调用时注入更多上下文

7. **优化模糊时间推理**
   - 使用当前时间作为参考
   - "待会儿" = 当前时间 + 30分钟

8. **添加输入预处理**
   - 识别并规范化时间表达
   - 提取关键实体（时间、地点、活动）
